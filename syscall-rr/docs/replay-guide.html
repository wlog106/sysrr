syscall-rr · replay side

Inside sysrr_replay

A restored process wakes up at the moment of the checkpoint. sysrr_replay answers each of its syscalls from the log made by sysrr, so the process lives through the same events again, without the original files, network or clock. New to the tool? Start with the walkthrough.

The idea

The checkpoint gives the starting state. The log gives everything the process learned after that. Feed it the same answers, and it computes the same state.

So we need a way to stop each syscall and answer it ourselves. The kernel has a feature for this, called seccomp user notification. It turns each syscall into a question to our program:

“Thread 1 wants read(3, buf, 16). What happens?”
“It returned 16, and here are the 16 bytes.” The real read never runs.

Other options didn't fit. This kernel can't override syscall results from eBPF. ptrace stops the process twice per syscall and conflicts with CRIU. A launcher can't work either, because a restored process never calls execve.

Getting started

A process can only install a seccomp filter on itself, and it must not run any syscall before that. So we make the frozen process install it, as if its own code had asked:

  1. Restore, frozenA line in /etc/criu/default.conf (leave-stopped) makes CRIU hand over the process stopped. The file is removed right after, or later checkpoints would freeze too.
  2. Take control for a momentptrace attaches, saves the registers, and writes a tiny syscall; int3 at the current instruction.
  3. Make it run our callsSet the registers and let it run: mmap a page, prctl(NO_NEW_PRIVS), seccomp(...). That returns a listener fd, and we copy it to ourselves with pidfd_getfd.
  4. Clean up and let goUnmap the page, close its copy of the fd, restore the code and registers, detach, send SIGCONT.

This takes a few milliseconds and happens after CRIU has finished, so the two don't conflict. Each process in the tree gets its own filter. A process forked later inherits its parent's.

One syscall

  1. TargetCalls read(3, buf, 16). The kernel parks it before running anything.
  2. sysrr_replayReceives the question and finds that thread's next record: read = 16, with 16 bytes.
  3. sysrr_replayChecks it's the same call, then writes the 16 bytes into buf with process_vm_writev.
  4. KernelReturns 16 to the target. The file was never read.

Addresses aren't in the log. A record says “argument 1”, and replay uses the pointer in the current call. It works because the restored address space matches the original.

Fake, run, or stop

Each call is first compared with the record:

CheckIf it fails
Same syscall?divergence The process took another path.
Same data going out (write text, paths)?divergence Its state has drifted. With -c, only a warning.
Same arguments?A warning.

Then it's answered one of two ways:

fake

Anything that touches the outside world: read, write, recv, open, stat, clock_gettime, getrandom, nanosleep. The call never runs, and the recorded result is returned.

run for real

Anything that changes the process itself: mmap, brk, clone, execve, futex, close, rt_sigaction, exit. Faking these would leave it without the memory or thread it expects. One exception: with -T, a recorded futex wait is answered from the log.

A wrong value only shows up when the process hands something based on it back to the kernel. That's why a divergence report also lists the thread's last five calls: the cause is often a little earlier.

Timing-only calls

Some calls only show how a thread got through a lock:

  • futex: did the thread have to sleep, or was the lock free?
  • clock_gettime(MONOTONIC): a timed wait reads the clock only if the lock was taken.
  • rt_sigreturn: did its child's SIGCHLD happen to arrive just then?
  • nanosleep: how often a thread polls is timing, and so is how long it sleeps.

These depend on nanoseconds, so a replay can legitimately differ. Replay treats their records as hints. A recorded one that doesn't happen is dropped, and an unrecorded one simply runs. With -v each of these is printed as drop or real, which shows where a replay starts to leave the recording. What really decides the outcome is the process's memory, which every thread sees.

Before this rule, Redis sometimes failed even with -S, because a lock was contended live and free in the replay. CLOCK_REALTIME stays strict, because programs print and store it.

Keeping threads in order

Each thread always gets its own results. The question is how threads run relative to each other. If they share memory, order changes the result. There are three modes:

ModeWhat it doesUse it for
DefaultEach thread follows its own list.One thread, or threads that share nothing.
-TOnly one thread runs user code at a time, in the order the threads reached their next call.Try this first for anything that shares memory, uses locks or forks.
-SSyscalls start in the recorded order. An early thread waits.Faster, for when threads rarely touch the same memory. It failed 2 of 9 runs on our two-thread test, while -T passed 6 of 6.

Why -T exists: nginx workers bump a shared counter right after accept4, with no syscall. Under -S, once A's call is answered, B's is released while A is still running, and the two race. Under -T, B waits until A reaches its next syscall.

Two calls count from when they started. A clone must run before its child's first syscall, even though it returns after it. An execve must run before a vfork parent can wake up. Without this, each side waits for the other forever.

Which thread goes first under -T

Between two syscalls a thread runs a stretch of user code. Live, stretches of different threads overlap. Under -T they run one after the other, so each pair that overlapped needs an order, and the log can't give it: touching shared memory makes no syscall.

Replay orders stretches by when they ended, which is when the thread entered its next syscall. Code that works under a lock usually makes a syscall right after releasing it, such as a futex wake or a write, so the end of a stretch is close to the moment that mattered. On six recordings of a thread pool, ordering by the end replayed four to the last line. Ordering by the start replayed one.

Programs built on locks need four more rules:

SituationWhat replay doesWhy
A recorded wait for a lock or conditionDoesn't run it. Holds it until its place in the order, then returns the recorded result.A real wait returns when the kernel likes. Four workers woken together would race for the lock again.
A thread found a lock taken and waitedRuns that thread after the one that held the lock.One at a time, nobody can find a lock taken.
The restore itselfKeeps every thread stopped with ptrace and starts them one by one, in the order of their first calls.A restored thread runs until its first syscall before seccomp can hold it. All of them at once is a race.
The thread whose turn it is waits for a lock that a later thread holdsLets the holder go first, if its call had already returned in the recording.The holder kept the lock across a syscall. Before this rule the replay stalled for 2 s and then guessed.

What's left is physical. If two threads release the same lock and enter the kernel within a few hundred nanoseconds, the log can show them in the wrong order. Replay then diverges at the first value that depended on it, and says so.

New threads and processes

A clone runs for real, so the kernel picks the new id. But the program has seen recorded ids: wait4 is faked, while fork and getpid are real. All of them must agree.

So replay sets the next id just before each clone, by writing to /proc/sys/kernel/ns_last_pid. That file acts on the writer's own pid namespace, so a small helper joins the target's namespace, forks a child inside it, and the child writes the number.

The tests create hundreds of processes and threads, and each one gets its recorded id. If the number is ever taken, replay prints a warning and matches threads by order instead.

Real file descriptors

A faked open = 3 creates nothing, so fd 3 doesn't exist. Faked reads don't care, but a real mmap(3) would fail. So replay puts a real fd at the recorded number with SECCOMP_IOCTL_NOTIF_ADDFD:

Recorded callWhat gets installed
open, openatThe same file, opened inside the container. If it's missing: a memfd for a file the target creates, otherwise /dev/null.
socket, acceptA socket of the same kind, never connected.
pipe, socketpair, eventfd, epoll, timerfd, memfdA new empty one.
dup, dup2A copy of the target's own fd.
An fd received over a socket; anything else/dev/null

Data still comes from the log. The fd only has to exist for the calls that run for real. close runs for real too, so the fd table stays the same as in the recording.

The supervisor is root on the host, so it opens files with openat2(RESOLVE_IN_ROOT). Without that, a symlink in the container to /etc/shadow would hand over the host's file.

New memory mappings

A real mmap may land elsewhere than in the recording, because CRIU can't restore the base address the kernel picks from. Allocators like jemalloc notice and take another path.

seccomp can't change arguments, but ptrace can. Replay interrupts the parked thread, sets the recorded address with MAP_FIXED_NOREPLACE, and lets the kernel restart the call. This takes a few hundred microseconds per mapping.

Signals

A signal makes a program run a handler at a moment it didn't choose. Replay handles two families differently. The first family happens at an exact point in the program:

SignalHow it's replayed
raise, kill, sigqueue to itselfThe call runs for real, so the kernel delivers the signal.
SIGSEGV from a bad pointerThe same instruction faults again. Nothing to do.
SIGPIPE from a write to a closed pipeThe write is faked, so no kernel code sends the signal. Replay sends it together with the recorded EPIPE.
sigwaitinfo, or a read from a signalfdRuns for real if the recorded signal is really pending. Otherwise it's faked.

SIGPIPE needs care. Sent while the thread is parked, it would make the kernel restart the write. Sent after the answer, it would arrive a little late. So replay uses ptrace for a moment: it interrupts the parked thread, puts the recorded result in its registers, queues the signal and lets go. The kernel then runs the handler first and the program sees EPIPE after it, as it did live.

Signals from a timer or from outside

The second family arrives when the clock or another program decides. The recorder logs every signal a thread receives, and which of its syscalls came just before. Replay uses that:

In the recordingWhat replay doesHow exact
The signal interrupted a syscall, such as a sleep or a read that was waitingWhen the copy makes that call, replay interrupts it the same way and sends the signal. The kernel then restarts the call or fails it with EINTR, as it did live.Exact
The signal came right after a syscall returnedSent together with that call's answer.Exact
The signal came while the thread was computingSent with the answer of the thread's previous syscall.Early, by the length of that computation. Replay counts these and says so.

Three details make it work:

  • Restored timers are switched off. A timer in the copy would fire by today's clock, while the program lives in recorded time. All timer signals come from the log instead.
  • Leftover signals are removed. A timer can run out while the copy sits frozen. That extra signal is taken out before the copy starts.
  • A signal that was waiting at the checkpoint is not sent twice. It's part of the photo: the restore delivers it, and the copy wakes up inside its handler. Replay notices and skips the recorded copy of it.

Signals the program's own threads send are left alone, because their kill runs for real. SIGCHLD is left alone too: the child processes are real and send it themselves, at their own time.

How a replay ends

When a thread runs out of records, its next syscall stays unanswered, unless it's a timing-only call, which runs for real so that other threads waiting on it aren't stuck. When all records are used, -e decides what happens:

OptionWhat happensUse it to
-e stop (default)Freezes the process. The tool keeps running.Look around with gdb or /proc.
-e liveRuns real syscalls from now on.Let it carry on from there.
-e killKills it.Scripts and tests.

A divergence ends it the same way. If nothing moves for 20 seconds, for example when threads wait on each other, replay reports that as a divergence and says who is waiting. If the target exits or crashes by itself, replay says so and stops. If the live run went on to exit normally and this one didn't, that counts as a divergence.

Keep the tool running. The filter can't be removed, so if the tool exits, the target's syscalls fail with ENOSYS.

The real pbzip2

pbzip2 0.9.4, built from a GitHub copy after removing three added sleep(10) calls. We couldn't compare that copy with the official release.

  • Unmodified, it never crashed: 0 of 365 runs, even on one CPU.
  • With two compile-time delays, it crashed in about 80% of runs. The code path is real, but the timing is forced.
  • The log finds the bug by itself: fault address 0x30, the offset of mut in the queue, at pbzip2.cpp:886, pthread_mutex_lock(fifo->mut). So a worker read fifo after main set it to NULL. You get this from the recording even if the replay diverges.
  • The replay matched only sometimes: the same crash in 3 of 9 crashing rounds in the main test, and the rest reported a divergence. Which worker wins the queue mutex isn't in the log.
  • Hidden crashes are real. A thread can fault just as another calls exit_group. The process exits 0 and looks healthy, but the recorder saw the fault. The report says another thread's exit_group got there first and hid this crash.
  • A replay crash means the bug is real, not that this is what happened. Replay only controls the order of syscalls. User code between them can race differently.

With -e live, the process carries on with stand-in fds: unconnected sockets and empty memfds.

Traps when restoring:

  • bad size: the target was growing a file during the checkpoint. Keep such files out of the container's writable layer.
  • can't write lsm profile -2: podman loads its AppArmor profile only when it starts a container. Run podman run --rm IMAGE true once after boot.
  • CRIU checkpointing failed -52: one cause is confirmed. CRIU refuses a checkpoint that lands while a TCP connection is open. Add --tcp-established to both podman container checkpoint and restore. Podman doesn't allow that option together with --name, so the copy keeps the original's name. -52 is CRIU's code for any failed checkpoint, so the real reason is only in its dump.log. The tests now print that reason when a checkpoint fails. An older note said the python test hit -52 about 1 time in 10. On 2026-11-12 it didn't happen once in 205 checkpoints and 14 full test runs, so that cause is unknown and no longer shows.
  • PID 1 ignores some signals: a container's first process ignores default-action signals sent from inside, so a test of SIGPIPE or SIGALRM needs a child process.
  • CRIU refuses some objects: an open POSIX message queue, or an inotify watch on overlayfs.
  • Same paths: a bind-mounted directory must exist at the same path on the replay machine.

Check yourself

Answer in your head, then open the answer.

1. Why can't a launcher install the filter and then start the program?

A restored process is rebuilt by CRIU in the middle of its life. It never calls execve, so nothing could run first. The seccomp() call has to be injected into it.

2. Replaying read(3, buf, 16) = 16: what happens to fd 3?

Nothing. The kernel parks the call, replay writes the 16 recorded bytes into buf and answers 16. The real read never runs.

3. A wrong byte goes in at a read, but the divergence appears two calls later. Why not at the read?

At the read, replay supplies the data itself, so there's nothing to compare. A difference shows only when the process hands out something based on it, here the next write.

4. Why does futex run for real, and why may its records be dropped?

It runs for real because a faked wait would let a thread continue before it should. Its records can be dropped because whether a lock was busy depends on nanoseconds, and the outcome is decided by the process's memory.

5. fork runs for real and wait4 is faked. How do their pids agree?

Just before the clone, replay sets ns_last_pid in the target's pid namespace to the recorded pid minus one. The kernel then hands out the recorded pid, and it matches what wait4 returns.

6. Two threads share a counter and print it. Which mode, and why?

Start with -T. Under -S, once one thread's syscall is answered, the other's can be released while the first is still updating the counter. -T waits until the first reaches its next syscall.

7. Why does -T order clone by when it started?

A child's first syscalls return before the parent's clone does. Ordered by return time, the child would wait for a record that needs the parent, and the parent's clone would wait behind the child. So nothing could move.

8. A faked open installs a real fd. Why must close run for real?

A faked close would leave the fd open. Real calls would then get different numbers than in the recording, and fds would eventually run out.

9. A shell script diverges at wait4. What's the likely cause, and is the tool broken?

The tool is working as designed. The shell's flow depends on when SIGCHLD arrived, and arbitrary signal timing isn't replayed. Reporting a divergence is the correct result.

10. You press Ctrl-C after a replay in stop mode, then send SIGCONT. What happens?

The listener closed with the tool, so each syscall the target makes now fails with ENOSYS. Keep the tool running, or use -e live.
