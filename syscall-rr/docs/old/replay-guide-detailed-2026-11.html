Inside sysrr_replay

How a restored container process is made to relive one recorded generation: every syscall it makes is paused by the kernel, answered from the log, and checked against what the original process did. Companion to the record-side guide, Inside sysrr.

Big picture

The whole trip

The recorder ends with a log whose generation 1 is everything the live process did after checkpoint 1. The replay starts from the checkpoint tarball and that log. Its job is to put the restored process into the state the live one reached, without the outside world (files, network, clock, randomness) being there.

The command line, end to end:

echo leave-stopped | sudo tee /etc/criu/default.conf     # for the restore only
sudo podman container restore --import ckpt.tar.gz --name replayed
sudo rm /etc/criu/default.conf
sudo ./sysrr_replay -p $(sudo podman inspect -f '{{.State.Pid}}' replayed) -g 1 rec.log
Design choice

Why seccomp user notification

Faking a syscall needs three powers: stop it before the kernel runs it, write the recorded results into the process's memory, and return any value. Only one mechanism on this machine has all three without tracing the process the whole time.

MechanismSkip the real call?Write user memory?Verdict here
eBPF bpf_override_returnOnly with CONFIG_FUNCTION_ERROR_INJECTION, which this kernel lacks; and only error-style returnsbpf_probe_write_user: unsafe, taints the kernelno
ptrace (like rr, strace)YesYesonly briefly Two stops per syscall; you rejected it for overhead
Launcher that installs seccomp, then execvesYesYesno A restored process never calls execve
seccomp RET_USER_NOTIF, injectedYes: reply with any value, or CONTINUE to run itYes, from the supervisor, with process_vm_writevused

The one idea to keep: with a user-notification filter, the kernel turns every syscall into a question to our program: "thread 1 wants read(3, 0x7ffd…, 16), what happens?" We can answer "it returned 16" after putting 16 recorded bytes at 0x7ffd…, and the real read never runs.

Step 1

Restoring the process stopped

If the restored process ran even one syscall before the filter was in place, that syscall would hit the real world and the replay would start out of step. So CRIU must hand the process over frozen.

CRIU has a --leave-stopped option, but podman doesn't expose it, and crun drives CRIU through libcriu, not the command line. CRIU does still read /etc/criu/default.conf in that mode. A one-line config therefore does it:

$ echo leave-stopped | sudo tee /etc/criu/default.conf
$ sudo podman container restore --import ckpt.tar.gz --name rrdst
restored pid 2393: State:	T (stopped)

Remove the file right after the restore. The option also applies to dumps: a later podman checkpoint --leave-running would leave the live container stopped. The test script backs it up, writes it, restores, and puts it back.

Step 2

Injecting the filter

A process can only install a seccomp filter on itself. So we make the stopped process call seccomp() as if its own code did, the same trick CRIU uses for its parasite. ptrace is held for a few milliseconds, after CRIU has finished, so nothing conflicts.

Details that matter

  • One injected syscall = set rax and the argument registers, set rip to the patched bytes, PTRACE_CONT, wait for the SIGTRAP of the int3, read rax. orig_rax = -1 is set so the kernel doesn't treat the stop as an interrupted syscall to restart.
  • Why mmap a page: the filter program has to be in the target's memory for seccomp() to read it. Writing below the stack pointer looks easier, but the kernel won't grow a stack for a remote write, so that page may not exist.
  • Why NO_NEW_PRIVS: without CAP_SYS_ADMIN (podman doesn't grant it), the kernel only accepts a filter from a process that has given up setuid gains. The flag stays set for the rest of the process's life.
  • The filter is seven BPF instructions: every native x86-64 syscall → SECCOMP_RET_USER_NOTIF. TSYNC puts it on every thread at once. It stacks on podman's own filter, and podman's denials (errno or kill) still win over our notification.
  • pidfd_getfd copies an fd out of another process's table, like dup across processes. The listener fd now exists in both processes, and the copy in the target is closed in step 8.
Step 3, repeated for every syscall

One syscall, end to end

Here is record #401 of the test, a read of 16 random bytes from /dev/urandom, replayed. /dev/urandom is never read; the thread gets exactly the bytes the original process got.

In code, steps 2 to 5 are supervise() → handle(). The notification and the reply are two small structs passed through ioctl on the listener fd:

struct seccomp_notif      { u64 id; u32 pid; u32 flags; struct seccomp_data data; };  /* data = nr, arch, ip, args[6] */
struct seccomp_notif_resp { u64 id; s64 val; s32 error; u32 flags; };              /* flags: CONTINUE = run it */

pid is the thread id as the supervisor sees it (host namespace). The recorder keyed threads by their id inside the container, which CRIU restores; ns_tid_of() reads the last field of NSpid: in /proc/<tid>/status to translate.

The decision

Fake, run, or stop

Each notification is matched against the thread's next record and goes through these checks in order:

CheckIf it failsWhy it exists
syscall number = recorded nrdivergenceThe process took another code path. Nothing after this can be trusted.
arguments = recorded args (up to the call's arg count)warningThe restored address space is identical, so even pointers should match. A mismatch is suspicious, but not always fatal.
D_IN / D_STR bytes = the thread's memory nowdivergence (warning with -c)The main detector. A process whose state drifted shows it at the next syscall that hands data to the kernel: the text of a write, a path, an address.

If all checks pass, the syscall is answered one of two ways:

fake  never runs

Anything that brings information in, or has an effect outside the process: read, recv*, clock_gettime, getrandom, stat, poll, write, send*, open, socket, nanosleep, …

Recorded D_OUT bytes are written into memory, and the recorded ret (or -errno) is returned. If the call created fds, real ones are installed at the recorded numbers (ADDFD).

run  CONTINUE

Calls that change the process itself: mmap, brk, mprotect, munmap, rt_sigaction, rt_sigprocmask, clone, futex, exit_group, getpid, close, chdir, …

Faking these would leave the process without the memory, thread or handler it now expects. The list is passthrough().

Side effect: replay runs faster than real time. A faked nanosleep returns at once, so the test's 2 seconds of recorded life replay in a few milliseconds. For a failure caused by an outside timeout, that also means time-based behaviour comes only from the recorded clock values, never from the real clock.

Placing recorded bytes

Where the bytes go

A data record doesn't store an address. It stores which argument the pointer came from (arg), a sub-buffer number (idx) and an offset. resolve() turns that into an address in the replayed thread, using the arguments of the syscall happening now:

Record saysSyscallsAddress
arg k, idx 0read, stat, clock_gettime, …args[k] + offset
idx ireadv / writev familyiov[i].iov_base + offset, with the iovec read from args[1]
idx 0xffffiov calls, recvmsgthe iovec array itself (compared, never written)
idx 0xfffe / 0xfffd / 0xfffcrecvmsg, sendmsgthe msghdr / its msg_name / its msg_control

All addresses are resolved before anything is written. Otherwise writing the recorded msghdr first could change the pointers that the later pieces are resolved through.

Memory is read with process_vm_readv and written with process_vm_writev. These are the two calls whose results the record guide's question 8 was about: the bytes the recorder copied at sys_exit come back here, byte for byte.

Faked opens, real fds

Real file descriptors (ADDFD)

A faked openat(...) = 3 returns 3, but nothing is opened: fd 3 does not exist in the replayed process. As long as every later syscall on fd 3 is faked too (read, fstat, close), nobody notices. But some calls run for real. mmap(fd 3) goes to the real kernel, which answers EBADF, and the process takes another path. tests/fd_target does exactly that, and with fd installation turned off (-N) the replay stops at its first line:

!! DIVERGENCE in thread 1 at record #510 (9 of 126 for this thread): input buffer differs
     arg1: 46 of 57 bytes differ, first at byte 11
       recorded  "iter 8 map=13.7 read=13.7 size=5 f=3 p=4,5 s=6,7 u=8 d=9."
       replayed  "iter 8 map=EBADF read=13.7 size=5 f=3 p=4,5 s=6,7 u=8 d=9"

The fix is a seccomp feature made for supervisors: SECCOMP_IOCTL_NOTIF_ADDFD copies one of the supervisor's fds into the target's fd table while the target is parked in the notification.

  • SETFD places the fd at exactly newfd, replacing whatever was there, like dup2. Without it the kernel would pick the lowest free number, which might not be the recorded one.
  • SEND answers the syscall with that number in the same step. Without it there would be a moment where the fd exists but the syscall is still pending.
  • Two numbers (pipe, socketpair) come back through memory, not the return value: two ADDFDs without SEND, at the numbers in the recorded int[2], then the normal reply.
Recorded callWhat gets installed
open, openat, openat2, creatThe same path, opened by the supervisor inside the container's root. O_CREAT and O_TRUNC are dropped (no side effects). Read-only if write is refused; /dev/null if the file doesn't exist here.
socketA socket of the same domain and type, made in the supervisor's network namespace. It is never connected; its traffic is faked anyway.
accept, accept4An unconnected socket like the listening one (its domain, type and protocol are read through pidfd_getfd).
pipe, pipe2, socketpairA fresh pipe or socket pair, both ends.
dup, dup2, dup3, fcntl(F_DUPFD)The target's own source fd, copied with pidfd_getfd: the same open file, as a real dup would give.
eventfd, epoll_create, timerfd_create, memfd_create, inotify_initA fresh object of that kind (a memfd stays empty: its writes were faked).
anything else that returns an fd/dev/null

The close-on-exec flag is taken from each call's own flag argument (O_CLOEXEC, SOCK_CLOEXEC, MFD_CLOEXEC, …). -v prints one line per installed fd: fd 3 <- file /etc/debian_version (cloexec).

Why close now runs for real. Before ADDFD, close was faked: there was nothing to close. Now every faked open leaves a real fd, so a faked close would leave it open, and the target's fd table would fill up with fds the recording had already closed. So close and close_range run for real, and the table follows the recording. If a number is already taken when an fd is about to be installed there, the two tables have drifted apart, and the replay prints a warning. For the same reason, chdir and fchdir now run for real: a relative open is resolved against the target's real working directory.

Why RESOLVE_IN_ROOT. The supervisor runs as root on the host. It opens /etc/x relative to /proc/PID/root, the container's root directory. Without a guard, an absolute symlink inside the container, such as /etc/x → /etc/shadow, would be followed on the host, and the host's file would be handed to the container. openat2 with RESOLVE_IN_ROOT makes /, .. and absolute symlinks stay inside the given directory, and RESOLVE_NO_MAGICLINKS refuses /proc/*/fd-style jumps.

Multi-threaded targets

Threads, and strict order with -S

The log is split into one queue per ns_tid, each in seq order. By default each thread just follows its own queue. That gives every thread the right results, but not the right timing relative to the other threads.

With -S, a thread's syscall is answered only when its record is the globally next seq. A thread that arrives early is parked: its notification stays unanswered, so the thread waits in the kernel.

tests/mt_target.c is built to show this. Two threads share an accumulator updated with an atomic compare-and-swap (no lock, so no syscall), and every printed line depends on which thread updated last:

ModeResult
per thread (default)diverged at record #889: T0 iter 54 acc 7b4c585d… recorded, 137a35ce… replayed. B overtook A because faked sleeps return at once.
-Spass 274 of 274 records in 3 threads, all 92 printed lines identical to the live process.

What -S does not control: it orders syscall entries, and therefore any user-space work that lies between two syscalls of one thread. Two threads racing in user space with no syscall between their accesses (the classic data race) still interleave however the CPU schedules them. For your goal of explaining a failure, a replay that diverges under -S exactly where a shared value is printed is itself a hint that such a race exists.

Threads created during the replay can get other ids than they had in the recording, because the restored pid namespace hands out ids its own way. Each recorded clone result is queued, and the next unknown thread to make a syscall is matched to it (thread_for()).

Edge cases

The edges of a generation

  • The start lines up by construction. From the record guide: a syscall the checkpoint interrupted is either re-run by both processes (the first record of gen 1) or turned into -EINTR for both. The restored process starts exactly where gen 1 starts.
  • Signal-interrupted records are skipped. A record whose ret is -512 … -516 (ERESTARTSYS and friends) means a signal interrupted the call in the live run, and the call was then issued again. The replay delivers no signals, so its thread makes the call once. Those records are dropped when the log is loaded, and so is a restart_syscall the replayed thread never makes.
  • The end of the test's recording is such a record: podman pause froze the live process inside nanosleep (-516). So 44 records in gen 1 became 43 to replay.
  • The clock. clock_gettime must be a real syscall to be faked. The vDSO answers it in user space otherwise, so the replay machine needs the same acpi_pm clocksource trick as the recording. The tests switch it on and back.
Reaching the goal

The end state

When a thread's queue is empty, its next syscall is held, unanswered. When every record has been consumed, the process is in the state the live one was in when the recording stopped, frozen at the entry of its next syscall. -e decides what happens then:

-eEffectUse it to
stop (default)SIGSTOP. The tool keeps running until Ctrl-C.Inspect the reached state: gdb -p, /proc/PID/. In the test, /proc/PID/syscall showed 230, the clock_nanosleep right after the last recorded call.
liveAnswer CONTINUE from now on: real syscalls.Let the process carry on from the reached state. The restored container printed iter 22, 23, … for real; the live one had stopped at 21.
killSIGKILL, exit.Scripts and tests.

A divergence ends the replay the same way. It prints the expected and actual call, the first differing byte, and the thread's last five replayed syscalls, then applies -e. With stop, the diverging thread is frozen at the syscall that showed the difference.

The filter cannot be removed. If the tool exits, every later syscall of the target fails with ENOSYS. So keep it running while you inspect, even in stop mode. For the same reason, CRIU cannot checkpoint the replayed process again.

Beyond toy targets

A real server: Redis

tests/test_redis.sh runs redis:7, which has six threads: the event loop, three bio_* background threads and two jemalloc_bg_thd. It loads 200 keys and checkpoints. Then redis-benchmark sends SET / GET / INCR / LPUSH on 1000 random keys from 20 concurrent clients, followed by a few redis-cli commands. Finally it takes DEBUG DIGEST, a hash of the whole dataset.

The restored copy is replayed with -S -e live. No client ever talks to it: every accept, read and epoll_wait of those 20 clients is answered from the log. Once the recording is used up, the copy runs for real, and its own DEBUG DIGEST must equal the live server's.

The first attempts failed in three new ways. Each failure exposed something the toy targets never exercised.

1. New mappings land somewhere else

!! DIVERGENCE in thread 1 at record #5152: different syscall
     expected  read(0x1b, 0x7faebad7b005, 0x4000) = 45
     actual    mmap(0, 0x600000, 0x3)
       #5151 mmap(0, 0x280000, 0x3) = 140388435734528     ← ran for real

mmap runs for real, and with no address given, the kernel picks the highest free gap below mm->mmap_base. That base is randomized at execve. CRIU restores every existing mapping at its old address, but it cannot restore mmap_base, so the restored process keeps CRIU's. #5151 therefore got a different address than in the recording. jemalloc wants its chunks aligned. The new address wasn't aligned, so it mapped a larger region (0x600000) to trim, instead of continuing to the recorded read.

seccomp can't change a syscall's arguments, but ptrace can, for that one call:

This uses ptrace again, but on one thread, for one syscall, after CRIU is done: a few hundred microseconds per new mapping. A Redis run pins one or two. mremap that moved a mapping is pinned the same way (MREMAP_FIXED, with the address in r8).

2. A thread with nothing recorded

!! DIVERGENCE: thread 6 (host 8772) is not in the recording; it calls futex(0x5594b55033e8, 0x189, 0)

Thread 6 is bio_close_file. It waited on a condition variable through the whole recorded period. A syscall that never returns is never recorded, so in some runs that thread has no record at all in generation 1. It is not a new thread. Now, when the tool attaches, every existing thread without records gets an empty queue, so its first syscall is held: it stays blocked, exactly as in the recording. Only threads created during the replay are "not in the recording".

3. Without -S, a lock taken in another order

!! DIVERGENCE in thread 9 at record #34123 (2 of 5 for this thread): different syscall
     expected  gettimeofday(0x7f5403ffb320, 0) = 0
     actual    futex(0x7f54062168f8, 0x80, 0x2)            FUTEX_WAIT_PRIVATE: a held mutex

A jemalloc_bg_thd woke up and found the arena mutex taken by the event loop, which had raced ahead of its recorded position. An uncontended mutex makes no syscall; a contended one does. So a different interleaving shows up as an extra futex. This is the mt_target lesson on a real program: with -S, the event loop is parked at its next syscall until the background thread's turn, and all 5 runs passed. test_redis.sh uses -S by default.

Practical traps hit on the way. The Redis image declares VOLUME /data. Removing the source container without -v leaves an anonymous volume behind, and the restore then fails with "volume … already exists". The throwaway container that loads the AppArmor profile now runs with --image-volume ignore. And ssh host "cmd > f &" keeps the ssh connection open until cmd exits, which in live mode is never, so the script starts the replay with setsid -f.

More than one process

Process trees: nginx and -T

tests/test_nginx.sh runs nginx with a master and two worker processes, using its own tests/nginx/nginx.conf. Each access-log line carries $request_id (from nginx's PRNG state in memory), $msec (the clock), $pid (which worker) and $connection. After the checkpoint, 220 requests arrive over 8 parallel keep-alive connections. The replayed tree must write the same log lines, and afterwards serve real requests.

One filter per process

A seccomp filter belongs to the process that installs it, with all its threads (TSYNC), and to children it forks later. The workers already exist when the checkpoint is restored, so the replay walks the tree under -p (parent links in /proc; CRIU left every process stopped) and injects a filter into each one before any of them resumes:

replaying generation 1: 2401 syscalls in 3 thread(s), recorded from nginx
seccomp listener attached to 3 process(es): 33504 33516 33517; resuming
== end of the recording reached ==
   replayed 2401 syscalls (faked 2004, ran 397), skipped 1 interrupted/restart records
   fds installed 127, fd warnings 0, mappings pinned 0

The supervisor polls all three listeners and answers each notification on the listener it came from. It uses the right process's pidfd for pidfd_getfd, and stops, continues or kills every process. The queues were already per container tid, so they needed no change. On the recording side, sysrr -f now also adds the processes that already exist under -p, not only later forks.

A race with no syscall in it

!! DIVERGENCE in thread 25 at record #1486 (63 of 879 for this thread): input buffer differs
     expected  write(0x5, 0x55e5704a14b0, 0x6a) = 106
     arg1: 1 of 106 bytes differ, first at byte 102          ← the conn= number

nginx's $connection is ngx_connection_counter, an atomic counter in a MAP_SHARED page the master created before forking. Each worker increments it right after accept4 returns, in user space, with no syscall. With -S, 1 run in 3 on claude-test diverged here; without it, 2 of 2 did.

A thread counts as running from the moment its syscall is answered until its next syscall reaches the supervisor. It doesn't count while it waits in a real blocking call (futex wait, rt_sigsuspend, wait4, exit). If a running thread doesn't come back within 2 seconds, the replay stops waiting for it, so a blocking call missing from that list can't freeze everything. With -T, nginx passed every run on claude-test, and Redis and mt_target pass too. It's still not a full guarantee. Two stretches that overlapped live now run one after the other, ordered by their start; if the live outcome was decided by nanoseconds inside both, the replay can still pick the other one.

The log order across workers is not the syscall order

Even in passing runs, a few lines from different workers sometimes appear in the other order than in the live log. The replay's -w capture follows the recorded order in which the workers entered write. The live log shows the order in which those writes landed in the shared stdout pipe. Two workers writing within microseconds of each other can land the other way round. So the test checks that each worker's own lines are identical and in the same order, and that the set of all lines is identical.

Two recorder bugs this target exposed

  • The empty-string quirk. nginx's image has an older glibc, whose fstat() is newfstatat(fd, "", buf, AT_EMPTY_PATH). bpf_probe_read_user_str() returns the length including the NUL ("abc" → 4), but for "" it returns 0, not 1. The recorder took 0 for a fault, flagged every such call F_FAULT, and reported the log as incomplete. Now "" is recorded as 1 byte.
  • The generation boundary is per thread. CRIU detaches threads one by one, and the recorder moved to the next generation only at the last detach. A thread detached earlier is already running again. In one Redis run the main thread made 8 syscalls in that 0.1 ms window, and they were stamped generation 0, so the replay of generation 1 started with the wrong syscall. Now each thread moves to the next generation at its own detach.
Know before you trust it

Limits

  • CONTINUE'd calls are not checked. seccomp never shows their return value. mmap and mremap addresses are pinned; if the pinned address were taken, that too would only show up later, as a divergence. Other address-choosing calls (shmat) are not pinned.
  • Installed fds are stand-ins. A socket is unconnected, a memfd is empty, and a file missing on the replay machine becomes /dev/null (so an mmap of it fails). That's fine during the replay; with -e live the process carries on talking to those stand-ins.
  • Not replayed: signals, io_uring (completions bypass syscalls), shared memory written by other processes, rdtsc, and vDSO time without the clocksource trick.
  • The filter is permanent, and no_new_privs stays set. See the end state.
  • Without -S or -T, threads or processes that share state may diverge. With -S, races that happen entirely in user space are not controlled. With -T, the user code between syscalls runs serially in recorded start order. Interleavings decided inside two stretches that overlapped live are still not reproduced, and neither is shared memory with processes outside the replayed tree.
  • Gaps in the recording (records flagged F_TRUNC, F_FAULT or F_LOST) are reported as a warning at load time, and the missing bytes are simply not injected.

Self-test

Check yourself

Answer in your head first, then open the answer.

1. Why can't the replay tool simply be a launcher that installs the seccomp filter and then runs the program, like the original plan?

A filter is installed by the process on itself and inherited across fork/execve. A launcher works for a program started fresh, but the restored process is recreated by CRIU from images: it never calls execve, and it is already "running" mid-program. So the seccomp() call has to be injected into it.

2. In the attach sequence, why does the injector have to answer the injected munmap and close, but not mmap or prctl?

Because munmap and close run after seccomp() has installed the filter, so they are already trapped and wait for a reply on the listener. If nobody answered, the target would hang in the injected syscall, and the injector would wait for the int3 forever.

3. A record says read(3, buf, 16) = 16 with a 16-byte D_OUT piece. List what the replay does, and what the kernel does.

Kernel: the filter returns USER_NOTIF, and the thread is parked before read runs. Replay: RECV the notification, map the host tid to its ns_tid, take the thread's next record, check that nr and args match, write the 16 recorded bytes at args[1] with process_vm_writev, then SEND val = 16. Kernel: the thread returns from the syscall with 16. Fd 3 is never read.

4. In the tampered test, the wrong byte was injected at #409, yet the divergence is reported at #411. Why not at #409?

At #409 nothing can be compared: the replay itself supplies that read's output. A divergence is only visible when the process hands data derived from the wrong input back to the kernel, which here is the next write. Divergence is detected on inputs (D_IN / D_STR), so its report marks where the drift showed, not where it started. That is why the recent-syscall history is printed.

5. futex is run for real, not faked. What could go wrong if it were faked?

A faked FUTEX_WAIT would return at once with the recorded value, while the lock or condition it waits for is not actually in the recorded state yet. The thread would carry on too early and race ahead of the thread that should have woken it. Run for real, the wait blocks until the replayed peer issues the real wake. Under -S, that wake is released in its recorded order.

6. mt_target diverges without -S but not with it. Name a two-thread program that would diverge even with -S.

Two threads that both do counter++ (or read and modify one shared variable) in a loop with no syscall between iterations, then print the value. -S only freezes a thread when it reaches a syscall. Between syscalls both threads run freely, and their increments interleave however the CPU schedules them, differently from the recording. This is the kind of race the record guide said neither the race check nor syscall replay can see.

7. After a successful replay in stop mode you press Ctrl-C, then later send the target SIGCONT. What happens?

The listener closed with the tool, so every syscall the target now makes fails with ENOSYS. Its first syscall (the held clock_nanosleep) returns an error, and the program goes on with broken results. Keep the tool running, or use -e live, if the process should continue.

8. With ADDFD on, why would leaving close faked break the replay, even though close brings no information into the process?

Every faked open now leaves a real fd at the recorded number. If the matching close were faked, that fd would stay open. Faked opens would still land at the recorded numbers, because SETFD replaces whatever is there. But real fd-creating calls, such as an mmap of a file or anything after -e live, would get the lowest free number, which is no longer what the recording had. Fds would also leak until EMFILE. Running close for real keeps the target's fd table equal to the recorded one; that is also why a "number already open" warning means the tables drifted apart.

9. The supervisor opens the container's files itself, as host root. A container's /etc/config is a symlink to /etc/shadow. What happens with plain open("/proc/PID/root/etc/config"), and what does the replay do instead?

A plain open follows the absolute symlink from the host's root, opens the host's /etc/shadow (the supervisor is root, so it is allowed), and ADDFD hands that fd into the container: an escape. The replay uses openat2(root_fd, path, RESOLVE_IN_ROOT | RESOLVE_NO_MAGICLINKS). Then /, .. and absolute symlinks resolve inside the container's root, giving the container's own /etc/shadow, exactly what the real open in the container would have reached.

10. Pinning an mmap works by interrupting a thread that is parked in a seccomp notification. Why does changing its registers at that moment change the arguments of the syscall it will run?

The interrupt makes the notification wait return -ERESTARTSYS, and the thread stops for ptrace on its way back to user space. Restart handling happens after that stop: since no signal handler runs, the kernel sets rax = orig_rax and moves rip back over the syscall instruction. The thread then executes the syscall again, and the arguments are read from rdi, rsi, rdx, r10, r8, r9 as they are now, after our SETREGS. Our filter traps the new attempt as a fresh notification, which shows the pinned address.

11. Under -S, worker B's accept4 is released right after worker A's, exactly in recorded order, yet the two workers can still end up with each other's connection numbers. Why, and what does -T change?

The counter is incremented in shared memory after accept4 returns, before the worker's next syscall. -S only waits for the right syscall entry: once A's accept4 is answered, B's is next in seq order and is answered at once, while A is still on its way to the increment. Both increments then race on two CPUs. -T doesn't release B until A has reached its next syscall, so A's increment is finished first. And because releases follow the recorded return times, A goes first exactly when A's accept4 returned first in the recording.
