Inside sysrr

How the recorder moves data between kernel and user space, how the decoder rebuilds each syscall from its pieces, and how a CRIU checkpoint becomes a clean boundary in the log. Line numbers refer to sysrr.bpf.c and sysrr.c.

The three pieces

Everything in sysrr is one of three things. Programs are small functions the kernel runs when an event fires: sys_enter, sys_exit and on_fork. Maps are memory that the programs and user space can both reach. The loader, sysrr.c, creates the maps, hands the programs to the kernel, and then reads results out of the maps.

Programs can't call each other across events, and they keep no variables between runs. Any information that has to survive from one event to the next, or reach user space, goes through a map. Global variables in a BPF program are maps too. That's why bpftool map show lists .rodata and .bss next to the maps you declared.

Follow-up questions

Records, chunks and scratch

A record (REC_*) is the unit everything is made of. The BPF side writes records into the ring buffer, sysrr.c copies them into the file unchanged, and sysrr_dump reads them back. Every record starts with the same 16-byte header (sysrr.h:58): type says which kind it is, len is the full size so a reader can skip it, and seq ties the records of one syscall together.

struct rec_hdr { u16 type; u16 flags; u32 len; u64 seq; };

file = [file hdr][DATA][SYSCALL][SYSCALL][DATA][DATA][DATA][SYSCALL][MARKER] ... [STATS]
TypeSizeWhat it is
REC_SYSCALL120 B, fixedOne syscall: nr, args, ret, timestamps, tids, gen, ndata. Numbers and pointers only, never buffer contents.
REC_DATA32 B header + up to 16 KiBOne chunk of user memory the syscall read or wrote. arg, idx and offset say where the bytes belong.
REC_MARKERfixedA CRIU event: seize, detach, new generation. Not a syscall.
REC_STATSfixedWritten once by user space at the end: totals and lost count.

A chunk is the part of one user buffer that fits in a single REC_DATA: at most CHUNK_MAX = 16 KiB. A bigger buffer is split into several chunks, at most CHUNKS_MAX = 64 (1 MiB). Anything beyond that isn't copied, and the syscall gets F_TRUNC.

Why one syscall becomes DATA, DATA, …, SYSCALL

getpid()                    → SYSCALL                               (no memory involved)
openat(AT_FDCWD, "/etc/x")  → DATA(D_STR path)  SYSCALL
fstat(3, &st)               → DATA(D_OUT struct stat)  SYSCALL
read(3, buf, 40000) = 40000 → DATA off=0     len=16384
                              DATA off=16384 len=16384
                              DATA off=32768 len=7232
                              SYSCALL ndata=3
readv(3, iov, 2)            → DATA idx=0 …  DATA idx=1 …  SYSCALL

The number and size of buffers vary

Zero buffers (getpid), one (read), N (readv), or several kinds (recvmsg: address + iovecs + control). No single C struct describes all of those; a fixed header plus self-describing pieces does.

BPF can't build one big variable record

reserve needs a constant size, the stack is 512 bytes, a per-CPU map value is at most 32 KiB. So a large buffer is copied 16 KiB at a time in a bpf_loop. Chunks exist because of these limits, not because the format needed them.

SYSCALL goes last: it's the commit

It carries what's only known after the data is out: ndata, and F_TRUNC / F_FAULT / F_LOST. The decoder checks "I have ndata pieces". DATA without a SYSCALL becomes "orphan", never attached to the wrong syscall.

A side benefit: most syscalls (close, futex, getpid) produce no DATA and cost a single 120-byte record. A format that reserved room for the largest buffer would spend kilobytes on every close().

When each buffer is copied: entry or exit

A buffer is copied at the moment it's known to hold what the kernel uses. That depends on its direction:

DirectionExamplesCopied atWhy
D_OUT, kernel writesread buf, struct stat, timespec, random bytessys_exitBefore the syscall the buffer holds garbage, and only ret says how many bytes are valid.
D_IN / D_STR, kernel readswrite data, paths, sockaddr, requested sleep timesys_enterThe kernel copies most inputs right after entry, and the syscall may then block for a long time. Copying early leaves another thread the shortest window to change the buffer in between. ret isn't known yet, so the requested size is copied.
in/outselect fd sets, poll revents, accept addrlen, recvmsg msghdrbothThe kernel overwrites the input with the result, so only the entry copy has what the program passed in.
execve pathexecve, execveatsys_enter onlyAfter a successful exec the old memory, path included, is gone.

Neither moment is exact under a race. The kernel doesn't freeze user memory during a syscall. It copies the buffer once, at a time of its choosing, and then uses only its own copy. If another thread changes the buffer, the entry copy can be wrong (the kernel copied later) and so can the exit copy (the kernel copied earlier). tests/race_target.c shows one of each:

write() to a full pipe   kernel copies late:  entry "AAAA…"  exit "BBBB…"   kernel took "BBBB…"  → entry copy wrong
open() of a FIFO         kernel copies early: entry ".../fifo" exit ".../XXXX" kernel opened fifo  → exit copy wrong

sysrr -r copies every pure input a second time at sys_exit (flag DF_EXIT), and sysrr_dump -r lists the syscalls whose two copies differ. That catches a buffer changed while a syscall used it. It can't see races that never touch a syscall (most race bugs: shared counters, missing locks), a change that's undone before exit, or a change to an output buffer after the kernel filled it. It costs about 11% extra on the dd worst case.

The price of copying at entry: the page may not be in memory yet, for example a string constant of a program that just started, and tracepoints can't fault pages in. When an entry copy fails, the input is copied again at sys_exit, after the kernel has touched the page. If the kernel never reads it either (a write to /dev/null), the record keeps F_FAULT.

What scratch is for, and why only DATA goes through it

scratch is a per-CPU buffer the size of one REC_DATA: 32-byte header + 16 KiB (sysrr.bpf.c:75). It's where one chunk is assembled before it's copied into the ring. One chunk = one pass through scratch = one REC_DATA; a 40000-byte read reuses it three times.

The split comes from one rule: bpf_ringbuf_reserve only accepts a size the verifier sees as a constant. A SYSCALL record is always 120 bytes, so it can be reserved and filled in place. A chunk's size is only known at runtime. Always reserving 16 KiB would work, but a 1-byte read would then eat 16 KiB of ring: the dd benchmark's 2M one-byte reads would overflow the 64 MiB ring almost immediately. bpf_ringbuf_output(ptr, n) takes a variable size, but it copies from memory that already holds the finished record, header in front. That memory can't be the user buffer (output needs kernel memory and a header) and can't be the stack (512 bytes). It has to be a map value, and per-CPU is the cheapest safe one: no locks, and safe because the syscall tracepoints run with preemption disabled. The price is one extra copy of at most 16 KiB.

In one sentence: SYSCALL = what was called and what came back; DATA = the bytes that crossed the user/kernel boundary, in ≤16 KiB chunks staged in scratch because their size is only known at runtime; same seq = same syscall, and the SYSCALL arrives last to close the group.

Your question 2

How sysrr_dump merges records by seq

One syscall becomes several records: zero or more REC_DATA (one per chunk of captured memory) followed by one REC_SYSCALL. They all carry the same seq. The REC_SYSCALL comes last on purpose, so it can carry the final flags and the count ndata. It "commits" the syscall.

Why the decoder can't rely on position

All CPUs write into the same ring buffer. If the target has two threads on two CPUs, their records interleave. The ring keeps the order in which space was reserved, and nothing more.

The decoder's algorithm (sysrr_dump.c)

for each record in file order:
    REC_DATA     → append to pending list           (don't print yet)
    REC_SYSCALL  → print it
                   take every pending DATA with the same seq, print them
                   if count != ndata, or flags has LOST/FAULT/TRUNC → "incomplete"
                   mark seq as seen in a bitmap
at end:
    leftover pending DATA          → "orphan data records"   (their SYSCALL was lost)
    holes in the seq bitmap        → "missing seqs"          (a SYSCALL record never arrived)

Two ordering guarantees make this work

DATA always comes before its SYSCALL

All of a syscall's records are written by the same thread, in order: inputs during its sys_enter run, then outputs and finally the SYSCALL during its sys_exit run. The ring hands out positions in the order they're requested, so earlier writes get earlier positions. The libbpf consumer also stops at any record that's reserved but not yet submitted, so it never skips ahead past one.

Seq numbers are unique

__sync_fetch_and_add(&seq_ctr, 1) is an atomic instruction. Two threads entering syscalls at the same moment on two CPUs always get different numbers.

Seq is assigned at entry, while records are written at exit. So in the file, seq numbers from different threads aren't in increasing order: a long read with seq 41 can commit after a quick syscall with seq 57. Within one thread they're always increasing. The decoder doesn't need sorted input; that's the point of the pending list.

Where preemption actually matters

Merging by seq doesn't depend on preemption at all. Preemption matters in two other places, which are easy to mix up:

depends on it the per-CPU scratch buffer

chunk_cb fills scratch and then copies it into the ring. If another run of the program could start on the same CPU between those two steps, it would overwrite the buffer halfway through. On this 6.12 kernel, syscall tracepoints run with preemption disabled, and BPF won't re-enter the same program on a CPU, so the buffer stays private to one run.

must not depend on it state from entry to exit

Between sys_enter and sys_exit a thread can sleep (a blocking read) and wake up on a different CPU. A per-CPU map would hand sys_exit the wrong CPU's data. That's why seq, args and gen live in tstate, which is attached to the thread and moves with it.

Rule of thumb: per-CPU storage is safe for work that starts and finishes inside a single program run. Anything that must survive until a later event belongs to the thread (task storage) or is keyed by thread id.

One quirk to know: if a thread is still blocked in a syscall when you stop recording, its seq was handed out but its REC_SYSCALL never gets written. If that syscall had inputs, their DATA records are already in the log; sysrr_dump sees they're newer than every committed syscall of that thread and reports them as "in flight at stop", not as orphans. If it had no inputs, nothing at all was written for it, and with several threads that shows up as a "missing seq" even though nothing was lost.

Your question 3

How CRIU is detected

Not just "is the syscall ptrace". It's a chain of four checks, and the last one does most of the work: is someone attaching to or detaching from one of our target's threads?

Why ptrace is the right signal

  • CRIU can't avoid it. To dump registers and run its parasite code inside the target, CRIU must PTRACE_SEIZE every thread. The bpftrace experiment saw exactly one SEIZE (0x4206) and one DETACH (0x11) per thread.
  • The pid argument is a thread id, possibly not the main thread. So the program looks the task up with bpf_task_from_pid() and compares the task's tgid. It must call bpf_task_release() on every path, or the verifier rejects the program.
  • The flag is written into the target's storage, not criu's. bpf_task_storage_get(&tstate, t, …) uses the task found by pid. Later, when the target makes a syscall, sys_enter sees seized = 1 and tags it F_DUMP.
  • The parasite can't be filtered any other way. Its syscalls really run in the target's threads, with the target's pid. Only "is this thread currently seized" tells them apart.

The counter that turns detaches into a generation

A process with 3 threads gets 3 seizes and 3 detaches. seized_cnt counts how many target threads CRIU currently holds. Each SEIZE adds 1. Each DETACH subtracts 1, and only when the count reaches 0 does gen go up and a NEW GENERATION marker get written. So one checkpoint is one generation, however many threads there are.

What it looked like in the real run

What it can't tell apart (yet)

  • Any tracer counts. If gdb or strace attaches to the target, sysrr treats it like a checkpoint. One fix: in handle_ptrace, check bpf_get_current_comm() for "criu".
  • It trusts the request, not the result. The state changes when ptrace() is entered. A SEIZE that fails would still mark the thread seized. Checking the return value in criu's sys_exit would close this gap.
  • A checkpoint without --leave-running kills the target after the dump. You get the seizes but no detach, so there's no generation 1, and nothing after it to replay anyway.
Looking ahead to replay

Multithreaded targets: the right result for the right thread

Every REC_SYSCALL carries tid and ns_tid. Replay uses those, not seq, to decide which thread a record belongs to. It matches on ns_tid, the id inside the container, because CRIU restores those while host tids change on the new machine. The mixed stream is never replayed as one queue; it's first split into one queue per thread:

log (seq order):   #10 T1 read   #11 T2 futex   #12 T1 write   #13 T2 read   #14 T1 close

split by ns_tid:   T1: #10 read  → #12 write → #14 close
                   T2: #11 futex → #13 read

When restored thread T2 makes a syscall, the replayer takes the next entry from T2's queue only, checks the syscall number (and input data) matches, and injects the results. Within one thread order is guaranteed: a thread can't be in two syscalls at once, so its syscalls are in program order with increasing seq.

What the order between threads affects

CasePer-thread queues enough?
Threads exchange data only through syscalls (T1 writes a pipe, T2 reads it)yes T2's read is faked from the log, so it gets the same bytes whenever it runs.
Threads share memory and the outcome depends on who goes first (locks, atomics, races)no T2 may reach a different state, ask for a different syscall, and the replay diverges.
Threads block on each other with futexDepends. Faking futex results can let a thread stop waiting too early and race ahead.

The log gives two orders between threads: seq is a total order of syscall entries (global atomic counter), and ring order / ts_exit is the order of exits. A stricter replayer can enforce "T2 may not finish seq 13 until every seq below 13 has been replayed", which reproduces how threads interleaved at syscall boundaries. It can't reproduce races on plain memory between two syscalls: those never enter the kernel, so no syscall recorder sees them. That's what rr does, by running all threads on one core and recording exactly when the scheduler switched, using hardware counters.

Three levels: (1) per-thread queues by ns_tid always give each thread its own results; (2) optionally enforce seq order to reproduce cross-thread syscall order; (3) shared-memory races are out of reach, so start with single-threaded or loosely coupled targets, and detect divergence (nr or input mismatch) and report it.

Loading: four steps

StepCodeWhat happens
opensysrr_bpf__open() sysrr.c:141Object parsed; nothing in the kernel yet.
configureskel->rodata->… sysrr.c:146–154Set constants; resize the ring buffer.
loadsysrr_bpf__load() sysrr.c:156Maps created, .rodata frozen, verifier runs.
attachsysrr_bpf__attach() sysrr.c:198Programs start firing.

volatile const globals go into .rodata. They can be changed until load, then the verifier treats them as known constants and drops code that can't run. volatile stops clang from baking in the source value 0. Plain globals go into .bss and stay writable.

Program type: tp_btf/sys_enter

One raw tracepoint for every syscall, with typed (BTF) arguments: struct pt_regs *regs, long id. Typing is what lets you write regs->di directly. x86_64 syscall arguments: di, si, dx, r10, r8, r9. The return value at exit is ret; the syscall number is regs->orig_ax.

Map types used

TypeMapWhy
RINGBUFeventsOne buffer shared by all CPUs, ordered, one reader. reserve/submit for fixed-size records (no copy); output for variable-size ones (copies).
TASK_STORAGEtstateOne struct per thread, freed when the thread exits, survives CPU migration. Can be reached for another task, which handle_ptrace relies on.
PERCPU_ARRAYscratch, lostA large buffer that doesn't fit the 512-byte stack; counters with no locking. Values are limited to 32 KiB, hence 16 KiB chunks.
HASHtargetsSet of tgids for -f.

Helpers and kfuncs

Helpers are the stable API: bpf_get_current_pid_tgid, bpf_probe_read_user (non-faulting copy from user memory), bpf_ringbuf_*, bpf_loop, bpf_get_ns_current_pid_tgid. kfuncs are kernel functions declared with __ksym. bpf_task_from_pid returns a reference that the verifier forces you to release.

Verifier rules that shaped the code

512-byte stack

The 16 KiB chunk lives in scratch, not in a local array.

Bounded sizes

if (n > CHUNK_MAX) n = CHUNK_MAX; before every variable-length copy, or the program is rejected.

Loop state

A bpf_loop callback must not carry counters between iterations. Compute the offset from the index i, or the verifier explores every value separately (the 1M-instruction failure).

Global functions

Non-static __noinline functions are verified once, for any arguments, instead of at every call site. Limit: 5 arguments, hence the packed tidk.

Atomics

__sync_fetch_and_add for shared globals. The versions that return the new value need -mcpu=v3.

References

Every acquired pointer (bpf_task_from_pid) must be released on every path; hence goto out.

Ring buffer wakeups

Flag 0 wakes the reader whenever it has caught up, and a fast reader is always caught up, so that meant one wakeup per syscall. sysrr uses BPF_RB_NO_WAKEUP until the ring is ¼ full and lets the reader poll every 10 ms. Markers use BPF_RB_FORCE_WAKEUP. This change took the dd slowdown from 5.6× to 2.9×.
