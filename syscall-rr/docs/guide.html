Inside sysrr

sysrr is a flight recorder for one container process. It writes down every syscall the process makes and every byte that goes in or out. Later, sysrr_replay uses that log to relive what happened. New to the tool? Start with the walkthrough.

The idea

A syscall is the only way a process talks to the outside world. If you know every answer the kernel gave, you know everything the process learned. So recording syscalls is enough to repeat its life later.

sysrr has three parts:

Programs

Small functions the kernel runs at each syscall entry and exit (sysrr.bpf.c).

Maps

Memory shared by those programs and user space. Programs keep nothing between runs, so everything goes here.

The loader

sysrr.c loads the programs, then copies finished records into the log file.

The log is a list of records

Every record starts with its type, its length and a number called seq. Records with the same seq belong to the same syscall.

RecordHoldsExample
REC_SYSCALLWhich call, its arguments, its result. Always 120 bytes.read(3, buf, 16) = 16
REC_DATABytes from a buffer, up to 16 KiB per record.the 16 bytes read returned
REC_MARKERA checkpoint event.CRIU attached, CRIU left
REC_STATSTotals, written once at the end.records lost: 0
 
getpid()                → SYSCALL
open("/etc/x")          → DATA(path)  SYSCALL
read(3, buf, 40000)     → DATA(16 KiB)  DATA(16 KiB)  DATA(7 KiB)  SYSCALL

The SYSCALL record always comes last. It says how many DATA records to expect, so a damaged syscall can be detected.

One syscall, start to finish

Here is write(1, buf, 29), step by step:

  1. EntryTake the next seq and save it with the arguments in tstate, this thread's private notes.
  2. EntryCopy the 29 bytes to the scratch buffer, then into the events ring as a REC_DATA.
  3. The kernelThe real write runs. The thread may sleep and wake on another CPU.
  4. ExitRead the notes back from tstate and write the REC_SYSCALL with the result.
  5. User spaceEvery 10 ms, sysrr.c empties the ring into the log file. It never looks inside.

In short: settings go down through .rodata before anything runs. Notes wait in tstate between entry and exit. Bytes pass through scratch and travel up through the ring to the file.

Which bytes, and when to copy them

A buffer is copied at the moment it holds what matters:

DirectionExamplesCopied atWhy
Kernel writes itread data, stat results, the timeExitIt holds garbage until the call is done.
Kernel reads itwrite data, pathsEntryThe call might block for a long time, and the program could change it meanwhile.
Bothpoll lists, recvmsg headerBothThe result overwrites the input.

A table in sysrr.bpf.c lists this for each syscall. On 2026-11-06, a new test found about 40 calls missing from it, including statfs, getxattr, sendfile, recvmmsg and timers. They are in now. Most ioctls are covered too, because their number says which way the data goes and how big it is.

sysrr -r copies each input a second time at exit and reports any buffer that changed during a call. That finds one kind of race only. It can't see most race bugs, because they never touch a syscall.

Putting a syscall back together

All CPUs share one ring, so records of different threads get mixed:

DATA #41   SYSCALL #57   SYSCALL #41
           ^ another thread finished here

That's fine. sysrr_dump holds DATA records aside until the SYSCALL with the same seq arrives. Two rules make this safe:

  • A syscall's DATA comes before its SYSCALL. One thread writes them in that order, and the ring keeps the order of requests.
  • Each seq is unique. __sync_fetch_and_add makes taking a number one atomic step, even on many CPUs.

Only scratch depends on preemption being off, because nothing may overwrite it halfway through a copy. The ordering rules above don't depend on it.

A thread still blocked in a syscall when you stop recording has a seq but no SYSCALL record. sysrr_dump -s reports that as a missing seq or as in flight, even though nothing was lost.

Spotting a checkpoint

To save a process, CRIU must attach to each of its threads with ptrace, and it can't avoid that. So sysrr watches for ptrace calls aimed at the target:

  1. SEIZECRIU attaches. sysrr marks the thread as seized and adds 1 to seized_cnt.
  2. While seizedCRIU runs its own code inside the target. Those syscalls get the flag F_DUMP, so replay ignores them.
  3. DETACHCRIU leaves. sysrr subtracts 1. At 0, gen goes up by one.

Generation N is everything after checkpoint N, which is exactly what a restore of that checkpoint must replay.

  • The check sits before the target filter, because the process calling ptrace is CRIU, not the target.
  • The pid CRIU passes is a thread id, so sysrr looks up that thread's process with bpf_task_from_pid.
  • Any tracer counts: attaching gdb looks like a checkpoint too.
  • A sleep interrupted by the checkpoint gets -EINTR in both the live and the restored process, so both continue with the next syscall.

Threads and child processes

Each record stores the thread's id inside the container (ns_tid). CRIU restores those ids, so replay can match each record to the right thread. Use sysrr -f if the target has child processes, or forks new ones.

A few records look odd but have a simple explanation:

In the logWhat it means
clone = 0, flag F_NOENTERA new thread or process being born. It comes out of its parent's clone without ever entering it.
sysfs = -1, flag F_NOENTERThe container's seccomp profile refused the call. The kernel skips the entry event but still reports the exit.
rt_sigreturnA signal handler finished. This used to show as syscall_-1, because this call overwrites the register that holds its number. sysrr now remembers the number from entry.
Result -512 to -516A signal interrupted the call, and it will run again.
==== thread N got signal S ... at rip R, FATAL ====A signal reached the thread. signal_deliver records it, with the fault address and the instruction. A signal that kills a thread is marked FATAL.
==== thread N ended: status ... ====The thread finished. sched_process_exit records its exit status. It may differ from the signal above: when one thread crashes the others get SIGKILL, and a default-action signal can show only here.

eBPF rules that shaped the code

RuleWhat the code does
Settings can change only before load.rodata is set between open() and load(). At load it freezes, and the verifier treats it as constants.
The stack is 512 bytesThe 16 KiB chunk lives in scratch.
reserve needs a constant sizeSYSCALL records use reserve and submit. Chunks vary in size, so they use bpf_ringbuf_output, which copies.
Loops must not carry countersThe verifier would explore each value separately (it failed at 1,000,001 instructions). Offsets are computed from the loop index instead.
Global functions are checked onceemit_buf isn't re-verified at every call site. The cost is a limit of 5 arguments.
Every reference must be releasedbpf_task_release is called on every path after bpf_task_from_pid.
Waking the reader is expensiveBPF_RB_NO_WAKEUP until the ring is ¼ full. Waking on every record made tracing 5.6× slower; now it's about 2.8×.

Commands

make
sudo ./sysrr -p PID -o rec.log       # record one process; Ctrl-C stops
sudo ./sysrr -f -p PID -o rec.log    # and its children
sudo ./sysrr -r -p PID -o rec.log    # also check for buffers changed during a call
sudo podman container checkpoint --leave-running -e ckpt.tar.gz NAME

./sysrr_dump rec.log                 # read the log
./sysrr_dump -s rec.log              # is it complete?
./sysrr_dump -g 1 rec.log            # only generation 1

For time to be recorded, clock_gettime must be a real syscall. Normally it answers in user space (the vDSO). Fix that on both machines with echo acpi_pm | sudo tee /sys/devices/system/clocksource/clocksource0/current_clocksource. The tests do this for you. It doesn't help time() or the coarse clocks: the vDSO answers those from a shared page whatever the clock source, so they're never recorded. Random bytes have the same gap on recent systems, because glibc's getrandom() also answers in user space, and this trick doesn't help there. The replay guide explains what happens.

One trap: if the target appends to a file in its container while you checkpoint, the restore fails with bad size. CRIU noted the size during the dump, and the file kept growing before podman archived it.
