sysrr Walkthrough

sysrr lets a copy of a running program live through the same events as the original. This page shows how, one click at a time. No kernel knowledge is assumed.

What it's for

A program in a container fails once a week. By the time you look, the moment is gone. You'd like to go back to a point before the failure and watch it happen again, as often as you need.

Two things make that possible:

  • A checkpoint is a photo of the program: its memory, its threads, its open files. A tool called CRIU takes it without stopping the program, and can bring a copy back to life from it later.
  • A recording is a list of everything the program learned from outside after the photo: bytes it read, the time, random numbers, network data.

A program is a machine that turns inputs into state. Start a copy from the photo, give it the same inputs in the same order, and it reaches the same state, including the same crash.

Every input reaches a program through a syscall, a request to the kernel such as read or clock_gettime. So sysrr records syscalls, and replays them.

Recording one call

The recorder never touches the program. It asks the kernel to run two small functions, one each time the program enters a syscall and one each time it leaves. That's what eBPF is: small checked functions that run inside the kernel.

Follow one read(3, buf, 16), a request for 16 bytes from file number 3:

Program
calls readread(3, buf, 16)
gets its answer16 bytes in buf
Kernel

does the readfills buf
exit hookresult, copy of buf
ring bufferrecords wait here
sysrr
copies to diskrec.log

Which bytes get copied depends on the direction. Data the kernel hands to the program (a read) is copied when the call leaves, because that's when it exists. Data the program hands to the kernel (a write, a file name) is copied when the call enters. The first kind is what a replay must give back. The second kind is what a replay uses to check that the copy is still on the same path.

The cost: a program that does nothing but tiny syscalls runs about 2.8 times slower while recorded. Ordinary programs lose far less. Other programs on the machine pay about 0.03 microseconds per syscall.

Where a replay starts

The recorder runs across the checkpoint, so the log holds calls from before and after the photo. A copy restored from the photo must only get the calls made after it. sysrr marks the border by itself, because it can see CRIU at work. Click the parts:

Take a second checkpoint later and generation 2 begins. One log can serve several checkpoints: restore photo N, replay generation N.

Replaying one call

On machine B the copy wakes up believing nothing happened. Its next syscall would ask machine B's kernel, which knows nothing of the original's files and network. So the kernel must not answer. A kernel feature called seccomp user notification does that: it parks each syscall and asks another program what to do. That program is sysrr_replay.

Copy

Kernel

The check is the useful part. A copy whose state has gone wrong, even by one byte, sooner or later hands the kernel something the original didn't. Replay stops there, shows both versions, and lists the thread's last calls. That report is the starting point for finding the cause.

Fake or run

Not every call can be answered from the log. A call that tells the program something about the outside is faked: the recorded result is returned and nothing really happens. Several threads

Each thread gets its own answers from the log, so one thread alone always replays exactly. Two threads that share memory add a problem: the result depends on who touched the memory first, and touching memory makes no syscall. Nothing in the log says who was first.

With -T, replay lets only one thread run program code at a time. It decides the order from what the log does have: the exact order in which threads entered their syscalls, and the calls threads make around locks. That is a well-founded guess, not a fact from the log.

How good is the guess? If two threads take the same lock more than a microsecond apart, it's right. If they do it within a few hundred nanoseconds, the log can show them the wrong way round. Replay then stops at the first value that came out differently and says so. It doesn't pretend.

What works today

The test suite runs 25 programs through the whole journey and compares each copy with its original. Measured on 2026-11-12, on one machine.

Signals from a timer or from another programreportedWhen they arrive isn't in the log.
Time and random numbers that never enter the kernelnot seentime(), and glibc's getrandom() on new systems. Reading the clock with clock_gettime works after one setting (below).

“Reported” means the replay ends by itself with a message that names the problem. A replay that hangs, or claims success when the copy differs, counts as a bug in sysrr.

Using it

Build once with make in syscall-rr/. You need root on both machines. The code is at github.com/wlog106/sysrr.

# machine A: make clock reads visible, then record
echo acpi_pm | sudo tee /sys/devices/system/clocksource/clocksource0/current_clocksource
PID=$(sudo podman inspect -f '{{.State.Pid}}' CTR)
sudo ./sysrr -p $PID -o rec.log            # add -f if the program starts child processes

# machine A, another terminal: take the photo, the program keeps running
sudo podman container checkpoint --leave-running -e ckpt.tar.gz CTR

# ... wait for the failure, then Ctrl-C in the sysrr terminal ...
./sysrr_dump -s rec.log                    # is the log complete?

# machine B: bring the copy back, frozen
echo acpi_pm | sudo tee /sys/devices/system/clocksource/clocksource0/current_clocksource
sudo mkdir -p /etc/criu
echo leave-stopped | sudo tee /etc/criu/default.conf
sudo podman container restore --import ckpt.tar.gz --name NEW
sudo rm /etc/criu/default.conf

# machine B: replay generation 1
sudo ./sysrr_replay -p $(sudo podman inspect -f '{{.State.Pid}}' NEW) -g 1 -T rec.log
OptionWhen to use it
-TThe program has threads or several processes. Safe to use always.
-e stop / live / killWhat happens at the end of the log: freeze the copy so you can inspect it (default), let it carry on for real, or end it.
-w FILESave what the copy prints. Its writes are faked, so they don't reach a terminal.
-vPrint every call as it's answered.

To try everything without a program of your own: tests/run_all.sh runs the suite, and tests/run_all.sh basic runs the smallest test.

Words

syscall
A request from a program to the kernel: read a file, send data, ask the time.
eBPF
Small functions the kernel runs for you at chosen moments, after checking that they're safe. The recorder is made of them.
CRIU
The tool that saves a running program to disk and restores it. podman container checkpoint uses it.
generation
The part of the log that belongs to one checkpoint. Generation 1 is everything after the first checkpoint.
seccomp
A kernel filter that sees every syscall of a process before it runs. Here it hands each one to sysrr_replay.
ptrace
The debugger interface. Replay uses it for a few milliseconds to install the filter in the frozen copy, and for a few special cases.
vDSO
Kernel code that runs inside the program to answer a few calls, such as the time, without a real syscall. Calls answered there can't be recorded.
futex
The syscall behind locks. A thread calls it only when it has to wait for a lock or wake a waiter, which is why the log shows only part of what locks did.
divergence
The moment the copy does something the original didn't. Replay stops and reports it.
